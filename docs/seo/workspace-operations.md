# SEOワークスペースの運用

開発・改修の窓口は「自社SEO AIOメディア構築」チャットへ統合する。コードの正本は `layrinc/layr-hp` のmain、作業はブランチとPRで管理する。この文書と同じフォルダの戦略・検証記録を引き継ぎに利用する。

## 管理画面

| 管理先 | URL | 対象となる公開URL |
| --- | --- | --- |
| 全体概要 | https://seo.layr.co.jp/ | 3施策の取得済みページ |
| 全国SEO | https://seo.layr.co.jp/regional/ | `/service/ltori/area/` |
| エルトリ採用ノート | https://seo.layr.co.jp/media/ | `/service/ltori/media/` |
| LAYR公式メディア | https://seo.layr.co.jp/articles/ | `/media/` |
| 共通の公開・運用 | https://seo.layr.co.jp/growth/ | エルトリの原稿・予約・接続・点検 |
| 共通戦略 | https://seo.layr.co.jp/strategy/ | 記事の選定・制作・改善方針 |

Cloudflare Accessの既存メール認証を共用する。認証許可リスト、Googleの権限、DBを増やす必要はない。

## 日々の確認

1. 全体概要で、各施策のPV・検索クリック・公開数と最終取得状況を確認する。
2. 改善対象の施策を開き、対象地域・記事と次の作業を確認する。
3. 新規記事は事業との関連、読者の判断段階、提供できる一次情報を確認する。同じ条件の候補では検索需要の大きい順に着手する。
4. 公開予約と運用の停止状態は「共通の公開・運用」で確認する。採用ノートの企画を「公開済み」にしても公開操作にはならない。
5. 記事の改善後は同じ対象範囲・期間条件で実績を見る。検索数とPV、検索表示とクリックを混同しない。

## 自動更新と保存

- GA4・Search Consoleの取得と点検は既存GitHub Actionsの毎日6:17（日本時間）。GitHub側の都合で開始が遅れる場合がある。
- 公開処理は既存の9:17と再確認の10:17。全国市は北海道から沖縄まで1日1県・47日間の予定で、当日担当県の確認済み全市を公開。採用ノートは暦月10本・3日以上の間隔で、承認された予約原稿だけが対象。公式メディアは独立した保留設定で制作・公開を止める。
- 管理画面の「最新の情報に更新」は保存済みデータの再読込。Googleの取得開始とは別の操作。
- 実績は既存D1で共有する。全国SEOの編集も既存 `/api/seo/state` へ保存する。
- 全国SEOの地域一覧は自動取得したSearch Consoleの実績を既定表示する。アクセス画面では「自動 GA4」「自動 Search Console」を切り替え、各取得元の期間を確認できる。手動CSV・Google接続の履歴は保持する。
- 検索語句ごとの地域詳細は既存の手動取得・CSVが対象。自動取得のページ実績と混同しない。
- 公式メディアの改善メモは `/api/seo/corporate/state` へ共有保存する。競合時は他者の保存内容を上書きしない。
- 採用ノートの企画・手動調査履歴は既存の端末保存。端末を移すときはJSONバックアップを使う。画面の統合によって企画が自動で端末間同期されるわけではない。

## 数値の扱い

- `—` は未取得・未計測・反映待ち等。実測の0と区別する。
- 集計は取得できたページの観測値。Googleが返さなかった行を0として補わない。
- GA4とSearch Consoleは集計方法・期間が異なることがある。表示される期間を確認する。
- 人数は記事や施策をまたいで合算しない。公式メディアの問い合わせ帰属は未対応で、概要の問い合わせ完了はエルトリの2施策で計測したものだけ。
- 取得に失敗した場合は最後に成功した実績を保持し、失敗状態を表示する。
- 市場検索ボリュームは外部調査結果を取り込む。自動取得元は未接続。提供元が0と返した場合だけ0表示の扱いを適用する。
- AI回答内の引用・推薦はGA4やSearch Consoleから推定しない。固定した質問と確認日時を記録して別に検証する。

## 開発時に保持するもの

地域マスター、既存D1の保存データ、公開原稿・予約、公開上限、Access認証、Googleの読み取り権限、定期ジョブを保持する。公開サイトの記事URLは管理画面のURL変更と分けて扱う。旧公開ドメインの管理画面は、旧ブラウザ保存データを取り出すための移行画面を維持する。

公開前にはCI、表示、取得範囲、欠損と0の扱いを検証する。本番反映後には認証済み画面と定期取得結果を確認し、実行したPR・本番バージョン・確認日時を記録する。
