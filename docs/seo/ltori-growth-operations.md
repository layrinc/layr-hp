# エルトリ全国SEO管理ツール 運用手順

更新日: 2026-09-21。現行コードの仕様をまとめた手順書です。本番反映やGoogle接続の完了報告ではありません。画面の実機検収状況・公開結果は別途確認します。

## 1. 開く場所と役割

| 場所 | 用途 |
| --- | --- |
| [地域・キーワード管理](https://seo.layr.co.jp/) | 対象市、狙うキーワード、進捗、地域ごとのメモを管理 |
| [集客・公開の運用管理](https://seo.layr.co.jp/growth/) | 原稿作成、公開予約、Googleの集計、問い合わせ・商談、点検 |
| `https://layr.co.jp/service/ltori/area/mie/tsu/` など | 検索から訪問する人が読む市ごとのLP |

管理画面はCloudflare Accessで認証します。許可された `biz.oneservice@gmail.com` でメール認証を完了してください。Googleのデータを読むサービスアカウントは、管理画面へログインするメールアドレスとは別です。

地域管理でキーワードや進捗を変えても、公開ページの本文は変わりません。新しい本文の公開は「集客・公開の運用管理」で行います。既存の静的ページと新しい運用原稿は区別され、既存静的ページの本文変更はリポジトリで行います。

## 2. 自動公開の動き

**毎日09:00日本時間に、承認済みで公開希望日時を過ぎた原稿を最大10件公開します。** Cloudflare Cron設定は `0 0 * * *` です。定時処理の実行状況は管理画面の履歴とCloudflare側で確認します。

- 対象は市のLPと採用コラムです。町・村・区のLPは追加対象にしません。
- 10件は上限です。公開可能な原稿が3件なら3件、0件なら0件です。
- 初期在庫は三重県の10市だけです。AIが毎日10件を無期限に生成する仕組みは含みません。継続するには次の原稿を作成・確認して公開待ちへ追加します。
- 初回10市は津、四日市、伊勢、松阪、桑名、鈴鹿、亀山、伊賀、尾鷲、志摩。初回Codexレビューを明記し、2026-09-22 09:00日本時間を公開希望日時としています。人間による承認と偽る記録は付けません。
- 上限は日本時間の日付単位で管理します。現行実装では、新規ページと既存運用原稿の更新版を合わせて10件です。
- 公開希望日時は「この時刻より前には公開しない」という条件です。15:00を指定した場合は、通常は翌日の09:00処理が対象になります。
- 承認時点の版だけを公開します。編集中の版、未承認の版は公開しません。処理が重なっても同じ版を重複公開せず、上限を超えないようデータベース側で判定します。

初回原稿の出典と判断は [初回10市の確認記録](./20260921-initial-editorial-review.md) にあります。少量公開という頻度だけで順位や検索ポリシーへの適合が決まるわけではありません。各市の採用担当者に役立つ内容を維持し、公開後の検索・相談データで改善します。

## 3. 次の原稿を公開待ちに追加する

1. 「原稿・公開予約」→「原稿を作成」を開きます。
2. 市のLPなら対象市、採用コラムならURL用の英数字スラッグを指定します。同じ市のページを複数作らず、既存原稿を確認してください。
3. タイトル、検索結果用の説明、見出し、導入文を入力し、読者を「企業の採用担当者向け」にします。
4. 本文を3節以上用意します。地域で確認した事実、その事実が採用案内に関係する理由、実際のLINEでの案内・対応手順を記載します。地名だけを差し替えた本文は使いません。
5. LINE活用の作例、根拠資料の名称・公開URL・確認日・対象地域を入力します。架空の募集は作例と明示し、自治体との提携や現地実績を推測して書かないでください。
6. 公開希望日時を日本時間で入力し、「下書きを保存」を押します。
7. 「保存した原稿をプレビュー」で市名、読みやすさ、根拠、サービス内容、問い合わせ導線を確認します。プレビューは認証が必要で、検索対象にはしません。
8. 確認後に「内容を確認して公開待ちに追加」を押します。承認者と承認対象の版がサーバーに記録されます。

必須項目、出典、地域名、検索意図、本文の重複などは機械的にも確認します。ただし、事実の正しさや文章の有用性を自動判定だけで保証する機能ではありません。保存後に文章を変更した場合は再度保存・プレビュー・承認を行ってください。

## 4. 停止・再開・同時編集

| 操作 | 起きること |
| --- | --- |
| 画面上部「自動公開を一時停止」 | 今後の定時公開を止めます。すでに公開したページは表示されたままです |
| 画面上部から自動公開を再開 | 条件を満たす予約原稿が次の定時処理から公開対象になります |
| 原稿単位の公開停止 | 対象原稿を公開対象から外し、公開中の運用ページも取り下げます。該当URLは通常404になります |
| 停止原稿を再開 | 内容を確認し、再承認して公開待ちに戻します |
| 公開中の原稿を編集・保存 | 現在の公開版を残したまま、次の版を下書きとして保存します。再承認後に更新します |

複数端末で同じ原稿を編集すると、古い版からの保存は競合として停止します。「最新の情報に更新」で読み直し、必要な変更を再入力してください。他の端末の変更を黙って上書きしません。

現在の下書きと公開版は分離していますが、すべての過去版を一覧から復元する機能はありません。公開・承認・停止の履歴と、定期的なバックアップを併用します。

## 5. 共通データと既存キーワードの移行

運用データはCloudflare D1の `SEO_DB` に保存します。キーワード管理、原稿、予約、商談、計測スナップショットを同じデータベースで管理し、認証済みの別端末からも参照できます。画面間でリアルタイムに自動反映する機能ではないため、別端末で更新した後は再読み込みしてください。

旧キーワード管理のブラウザ内データは、**同じドメイン・同じブラウザで開き、共通保存先がまだ空の場合**に初回移行します。旧データは元のブラウザにも残ります。共通保存先にデータがある場合は自動合算しません。

以前の別ドメインやプレビューURLに保存したデータは、そのページの「JSONバックアップを保存」で書き出し、新管理画面で内容を確認して復元します。既存の共通データがある場合は先にそのバックアップも保存し、置き換え内容を確認してください。キーワード用JSONと、後述の全運用データ用バックアップは別形式です。

D1未接続時は保存できないことをエラーとして表示します。未接続のまま端末内へ保存して成功扱いにはしません。公開前に、本番Workerへ正しいD1を `SEO_DB` として接続し、管理画面での読み書きを確認します。

接続先は `wrangler.jsonc` の `database_name: "layr-hp-seo-db"` で明示しています。Wranglerは既存データベースを名前で取得して接続するため、デプロイごとに別のD1を増やしません。この名前を他サービスのデータベースへ変更しないでください。

## 6. Google連携を設定する

Google側の権限設定と、Cloudflare Workerのサーバー設定が必要です。管理画面へ秘密鍵を入力する操作はありません。

1. 対象のGoogle CloudプロジェクトでGoogle Analytics Data APIとSearch Console APIを有効化します。専用サービスアカウントを用意します。[Analytics API公式手順](https://developers.google.com/analytics/devguides/reporting/data/v1/quickstart)、[Search Console API認証](https://developers.google.com/webmaster-tools/v1/how-tos/authorizing)
2. GA4の対象プロパティのアクセス管理に、サービスアカウントの `client_email` を閲覧者として追加します。検索結果用の管理画面ログインアドレスを追加する操作とは異なります。
3. Search Consoleの対象プロパティにも同じサービスアカウントをユーザー追加し、検索パフォーマンスとURL検査結果の閲覧ができる権限を付けます。所有者にする必要はありません。ユーザー追加は対象プロパティの所有者が行います。[Search Consoleの権限管理](https://support.google.com/webmasters/answer/7687615?hl=ja)
4. サービスアカウントのJSON鍵を用意し、本番Workerへ次の3項目を設定します。鍵はチャット、Git、公開ページへ貼り付けません。

| Worker設定名 | 入れる内容 |
| --- | --- |
| `SEO_GOOGLE_SERVICE_ACCOUNT` | サービスアカウントのJSON全体。CloudflareのSecretとして保存 |
| `SEO_GA4_PROPERTY_ID` | GA4の数字だけのプロパティID。`G-` で始まる測定IDではありません |
| `SEO_GSC_SITE_URL` | 権限を付けたプロパティと完全一致する `sc-domain:layr.co.jp` または `https://layr.co.jp/` |

5. 設定を本番Workerへ反映し、「接続・サイト点検」で設定状態を確認します。
6. 「Googleデータを取得」を実行し、少し待って「最新の情報に更新」を押します。開始の受付と同期完了は別です。最終成功日時と取得エラーを確認してください。

この実装が要求するOAuthスコープは `analytics.readonly` と `webmasters.readonly` です。読み取り用に限定し、Google側の設定変更、URL送信、インデックス登録申請は行いません。URL検査はGoogleが保持している状態の取得であり、今のページをライブ検査する機能ではありません。[URL Inspection API](https://developers.google.com/webmaster-tools/v1/urlInspection.index/inspect)

## 7. 数字の見方と毎日の処理

「成果・改善」ではページ別の検索表示・クリック・PV・問い合わせ完了と、商談管理の記録を確認できます。「次に改善するページ」は、得られたデータと点検結果から確認理由を出します。売上増加や順位向上を自動で確約する評価ではありません。

- Google同期とサイト点検は毎日06:15日本時間に実行する設定です。Cronは `15 21 * * *`。手動でも実行できます。
- 比較対象は、UTCの日付で3日前を末日とする28日間と、その前の28日間です。当日・昨日の速報値ではありません。
- GA4はプロパティのタイムゾーン、GSCは太平洋時間を基準とするため、同じ日付でも日次の区切りが異なります。
- 未設定、未取得、対応する行がない数値は「—」です。実測の0件と区別します。同期失敗時は直前の成功データを残し、成功日時とエラーを表示します。
- 1レポート・1期間あたりの取得上限は4,000行です。上限到達、しきい値、サンプリング等の注意を確認します。GSCで非表示となる検索語句など、すべての検索を回収することはできません。
- ページごとのユーザー数を合計しても、サイト全体の重複を除いたユーザー数にはなりません。PV、入口ページのセッション、問い合わせは別の指標です。
- 検索語句と個々の問い合わせを一対一で特定する機能はありません。

Google URL検査は**UTCの日付で最大10URL/日**、サイトのHTTP点検は1回最大10URLです。確認の古いページから順に見ます。全URLを毎日検査する仕様ではありません。HTTP点検は応答、canonical、noindex、主要見出し、問い合わせリンクなどが対象で、フォーム送信の成功まで自動保証するものではありません。

## 8. 問い合わせから受注まで

新しい問い合わせ受付 `/api/ltori/contact` を通った送信は、メール受付サービスが成功を返した後に商談管理へ記録します。ボタンのクリックやフォームへの入力だけを問い合わせに数えません。同じ送信IDの再試行は重複登録を防ぎます。

運用データベースへ保存するのは管理番号、受付日時、流入ページ、進行状況、入力された金額などです。問い合わせの氏名・メールアドレス・本文は商談一覧へ複製せず、既存のメール送信先へ届けます。

1. 「問い合わせ・商談」で新規相談を確認します。
2. 採用LINEを検討する企業の相談と確認できたら「有効な相談」へ進めます。
3. 打ち合わせ中は「商談中」、成約時は「受注」、終了時は「見送り」へ変更します。
4. 受注額と粗利益は実際の数字が確認できた時点で入力します。空欄を0円や想定売上に置き換えません。

メール受付後にデータベース保存だけが失敗する場合もあります。メールの管理番号を確認し、重複がないことを見て手動で補います。電話、直接のメール、LINE上の相談など、このフォームを通らない接点も「商談記録を追加」で記録してください。流入ページが分からなければ空欄にし、氏名やメールアドレスを管理番号欄へ入れません。

GA4の問い合わせイベントと、サーバーで受理した問い合わせ・商談は別集計です。計測拒否などで差が出るため合算しません。商談の段階別件数は現在の状態であり、過去に一度でも各段階へ到達した累計ファネルではありません。

## 9. バックアップと復旧

大きな変更の前と定期的な運用日に「バックアップを保存」を押します。全運用データのJSONには原稿、公開版、公開履歴、商談、キーワード管理、計測・点検結果などが含まれます。Googleの秘密鍵は含みません。社内のアクセス制限された保存先で管理してください。

管理画面の全運用バックアップはテーブルを順番に読み出します。書き込みが多い最中の完全な時点復元用スナップショットとは異なります。移行や大きな復旧に備える場合は、自動公開と関連する書き込みを止め、開発担当がD1のバックアップも確保します。

| 戻したい対象 | 対応 |
| --- | --- |
| 原稿の文章 | バックアップから戻す内容を確認し、下書きとして保存・プレビュー・再承認。次の公開枠で反映 |
| 誤ったページの緊急取り下げ | 原稿単位で公開停止。全体の自動公開停止だけでは既存ページは消えません |
| 旧キーワード管理のJSON | キーワード管理の専用復元画面で内容を確認して復元 |
| D1を含む全運用データ | 開発担当が現状も退避し、停止中に復元計画を確認して対応。全運用JSONのワンクリック復元UIはありません |
| Workerのプログラム | 正規のデプロイ経路で以前のコードへ戻す。コードを戻すだけではD1のデータは戻りません |

復旧では公開済みの履歴と日次上限の記録を不用意に消さないでください。重複公開や古い予約の再実行につながります。復旧後は認証、共通保存、対象ページ、予約、問い合わせ受付、Googleの最終成功日時を確認してから定時運用へ戻します。

## 10. 長期運用の確認事項

毎週、次の公開原稿の在庫、出典の確認日、企業からの有効な相談、公開停止・接続エラーを確認します。月ごとに検索語句、入口ページ、相談から受注までを見て、表示はあるがクリックされないページや、訪問されても相談につながらないページの改善を決めます。

公開量を増やす場合も、未承認原稿を数合わせで公開しません。現段階では無限の原稿生成、Googleへの自動登録申請、メール・Slackへの自動通知、すべての過去版のワンクリック復元は含まれていません。
